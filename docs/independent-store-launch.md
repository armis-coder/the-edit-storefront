# Independent store launch

## 1. Database and hosting

Create a hosted PostgreSQL database, for example Supabase or Neon. For serverless hosting, use the provider's supported pooled connection URL with TLS and a user permitted to create the private `edit_store` schema. The browser never receives database credentials. This schema revokes access from `PUBLIC`; do not expose it through a public REST API or grant anonymous access. Keep preview/testing and production databases separate.

Use commercial-eligible hosting. Vercel Hobby permits personal, non-commercial use only; sales require an eligible plan or another Node.js host. Independent commerce still needs hosting, database, email and maintenance. This implementation makes no purchases or upgrades.

## 2. Private environment variables

| Variable | Value |
| --- | --- |
| `COMMERCE_PROVIDER` | `independent` |
| `DATABASE_URL` | Private PostgreSQL connection URL |
| `SITE_URL` | Canonical public HTTPS origin, without a path |
| `ADMIN_EMAIL` | Owner sign-in email |
| `ADMIN_PASSWORD_HASH` | Generated on your computer with `npm run store:credentials` |
| `ADMIN_SESSION_SECRET` | Generated by the same command |
| `RESEND_API_KEY` | Email service key for automatic notifications |
| `STORE_EMAIL_FROM` | Verified transactional sender |
| `STORE_ORDER_EMAIL` | Owner alert inbox; defaults to store contact email |

Enter these directly in the host's private environment settings. Do not send credentials in chat or use `NEXT_PUBLIC_` prefixes. Never enable `STORE_DEVELOPMENT_DB` in production. Rotating either owner credential invalidates sessions. Redeploy after changing environment values.

`SITE_URL` is the allowed mutation origin. Preview deployments need their own matching origin and test database. Redirect www/apex aliases to the canonical origin.

On a non-Vercel host, set `STORE_TRUSTED_IP_HEADER` only if a trusted reverse proxy overwrites that header on every request and is the only route to the Node.js server. Otherwise requests share a conservative fallback rate limit. Vercel uses its platform-injected header automatically.

## 3. Initialize and deploy

Run `npm run store:migrate` with private configuration, or let the first independent-store request initialize the schema. Initialization is transactional and serialized across server instances. Collections are empty and checkout closed; no demo stock is inserted.

Deploy the GitHub repository using the Vercel Next.js preset or `npm run build` and `npm start` on a Node.js host. Do not set `dist` as the Next.js output directory or use a static export. Sign in at `/admin`; verify HTTPS, login/logout and anonymous admin API rejection on the real host.

## 4. Catalogue, delivery and policies

In **Products**, add genuine items, accurate descriptions, variants/SKUs, prices, available stock, actual images and realistic dispatch estimates. Image uploads accept still JPG, PNG and WebP up to 5 MB; the server strips metadata, resizes and converts to WebP. Images are stored in PostgreSQL for the initial small catalogue; include the media table in backups.

Draft/archived items are hidden. Restricted products cannot be bought until cleared following an actual category review. Set stock conservatively, including only supplier-confirmed quantities. Orders reserve stock immediately; cancel invalid orders to release it. The software does not order from suppliers automatically.

In **Settings**, enter supported cities, shipping fee, any free-delivery threshold, contact details and truthful delivery/returns/privacy policies. Enable COD and/or bank transfer; add bank instructions for transfers. The admin rejects opening checkout without these essentials. Keep checkout closed during preparation.

The initial catalogue uses the existing six collections and a 500-product list limit. Subscriber view is capped at 1,000. Extend pagination before reaching those limits.

## 5. Email, backups and maintenance

Verify a Resend sender and configure its private environment variables. Orders survive email failures; queued messages can be retried in admin. Failures have a five-minute cooldown and ten-attempt ceiling. Check pending notifications and the email dashboard daily; investigate exhausted jobs before resetting them. Receipt and owner-alert emails are implemented; shipment status is available on private receipts, with no automatic shipment email in this release.

Configure database backups and test restoring them. Use provider backups or encrypted PostgreSQL dumps stored off the application host. They contain customer addresses/contact details and images, so restrict access and retention. Monitor errors, database capacity and email delivery. Free database tiers can have availability and backup limitations; consider these before accepting paid orders.

## 6. Controlled real-host test before advertising

Open checkout for a controlled test with a clearly labelled test item and actual test delivery address. Check desktop, phone and keyboard operation. Verify prices/shipping, owner order visibility, email arrival, private receipt access, image loading and duplicate-request behavior. Confirm bank-transfer processing is blocked until payment is verified, shipment needs tracking and cancelling restores stock once. Check paid cancellation/refund records.

Cancel the test order and archive the item. Close checkout again if anything fails. Local automated tests do not certify production PostgreSQL/TLS, actual email delivery or courier arrangements. Open the store for customers only once this test and operations are ready.

## 7. First-order workflow

1. Customer checkout creates a **pending** order and reserves stock.
2. Verify contact/address, supply and delivery feasibility. For bank transfer, check the bank account and record **paid**. For COD, confirm with the customer before dispatch.
3. Mark **confirmed**, then **processing**. Buy from the supplier or pack owned stock manually.
4. Book the courier manually; enter courier/tracking and mark **shipped**. The private receipt shows tracking.
5. Record delivery and payment, then mark **delivered**. Reconcile COD courier remittance separately; customer delivery and courier payout are distinct events.
6. Cancel pre-dispatch orders that cannot be fulfilled. Paid cancellation becomes **refund due**. Make the refund externally, then record **refunded**. Returned delivered items require manual inspection/restocking; refunding does not automatically add stock.

This first release has guest checkout, one owner account and manual fulfilment. Customer accounts, staff roles/MFA, card gateways, discount systems, automated courier/supplier integrations and automated returns are not included. The owner remains responsible for orders, refunds, backups and software maintenance.
